# CloudDock worker\n\nThe worker polls the Supabase Edge Function control plane (type-checked in CI), claims queued jobs, and runs **bot workloads only** using the allowlisted Node.js and Python images. It does not currently provision Minecraft or website workloads.\n\n## Requirements\n\n- A dedicated Linux VM for CloudDock workloads. Do not run untrusted customer workloads on a personal computer or a host containing private data.\n- Docker Engine installed and running.\n- A Supabase project with migration `0002_hosting_control_plane.sql` applied and the `control-plane` Edge Function deployed.\n- A long random `CLOUDDOCK_WORKER_TOKEN` (at least 32 characters), shared only with the Edge Function and this worker.\n- `CLOUDDOCK_SECRETS_ENCRYPTION_KEY`: base64 encoding of exactly 32 cryptographically random bytes. Keep a secure backup; losing it makes stored environment secrets unrecoverable.\n\n## Setup\n\n1. Copy `.env.example` to `.env` and fill in the function URL, worker token, worker name, region, and memory capacity.\n2. Set `DOCKER_GID` to the group ID owning `/var/run/docker.sock` on the VM.\n3. Create the host data directory `/var/lib/clouddock/services`.\n4. Build and start with `docker compose up -d --build`.\n5. Confirm the worker appears online in `hosting_workers` and submit a test bot service.\n\nThe worker requires access to the Docker socket, which is effectively host-administrator access. Run it only on a dedicated, disposable worker VM. Never mount the Docker socket into customer containers. Customer containers are launched with CPU, memory, PID, read-only root filesystem, dropped Linux capabilities, no-new-privileges, a non-root UID, no published ports, and a dedicated bridge network.\n\n## Source archive\n\nUpload a ZIP from the service card in CloudDock. For Node.js, put `index.js` at the archive root (and `package.json` / `package-lock.json` if needed). For Python, put `main.py` at the root and optionally include `requirements.txt`. The current worker starts `node index.js` or `python main.py`; it does not yet support custom Dockerfiles, arbitrary startup commands, interactive console, Minecraft, or static website hosting.\n\n## Network hardening\n\nThe worker creates a dedicated Docker bridge with inter-container communication disabled. Before accepting public workloads, configure host firewall rules to prevent customer containers from reaching host management ports, private LAN ranges, cloud metadata endpoints, the Docker API, and other tenant networks. Restrict outbound traffic to the minimum needed for bot APIs and package downloads. Do not expose container ports directly from this first worker implementation.\n\n## Operational limits\n\nThe worker currently processes one job at a time and uses conservative per-service CPU/memory limits. It calls control-plane reconciliation every 30 seconds: workers missing heartbeats are marked offline, abandoned jobs are requeued up to three attempts, and exhausted jobs are marked failed with a customer-visible event. This is basic recovery, not high availability. Logs are not yet streamed to the dashboard. Do not advertise production SLAs until capacity-aware scheduling, monitoring, alerting, and backups are in place.\n
